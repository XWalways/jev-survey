一页看懂

从一句话定义、三个类比和五个关键指标，理解 Jev 如何把输入材料转成可直接用于代码分支的判断。

一句话定义

Jev 是一个「不写字」的 AI 模型。你给它一段材料（state）和一组你预先定义好选项的问题（questions），它直接返回带概率分布和置信度的结构化答案——没有聊天、没有流式输出、没有自然语言生成。

官方原话（来自发布博客）：

Think of Jev as a frontier-intelligence function call: unstructured state in, typed probabilistic decisions out. （把 Jev 想成一次前沿智能的函数调用：非结构化 state 输入，类型化概率决策输出。）

三个类比（帮你 30 秒建立直觉）

类比 说法 说清了什么 说漏了什么
智能 if 语句 Jev 是嵌在代码里的「模糊判断版 if」——if Jev(state, "这是账单问题吗").noul > 0.9 说得最准：它的产出就是给代码分支用的 漏了「零样本泛化」——传统 if 不能理解新情况
智能决策网关 Jev 是 LLM 与规则引擎之间的「决策位」，负责高频原子化的快判断 说清了它和 LLM 的分工关系 漏了它自身也能独立承担大量原本交给 LLM 的判断
概率分类函数根据输入材料与预设标签，返回结构化分类结果及概率分布。明确了它的固定输出接口与决策用途需要结合零样本泛化、校准与任务数据评估效果

形态与架构

System One 接收非结构化材料，输出预先定义好的结构化决策。本章梳理官方定义、已公开的架构信息与数据流。

System One 的官方定义

来自 https://docs.typesafe.ai/concepts/system-one：

System One models are a class of AI models built to make fast, structured decisions that software can use directly. A System One model evaluates a state and returns typed answers and probabilities. Jev is TypeSafe's flagship model and the first System One model. Like an LLM, a System One model understands natural-language input. It returns typed decisions and probabilities rather than generated text. Jev currently accepts text input only. It evaluates strings, JSON objects, and arrays of text. Images, audio, and video are not supported (yet).

System One 与 LLM

这是理解 Jev 最重要的一张表，来自官方发布博客：

维度 现有 LLM System One + Jev
训练优化目标 RLHF（人类反馈强化学习）/ RLVR（可验证奖励强化学习） RLCD（Reinforcement Learning for Calibrated Decisions，校准决策强化学习）
优化什么 人类评分者偏好的长文本与聊天回复；可被程序化验证的输出 在 System One 任务上，具备认知诚实的概率的答案
输入 非结构化数据（如文本），侧重连续消息序列 非结构化数据（如文本），侧重结构化程序状态
输出 字符串 / 生成文本。灵活、可以是任何东西：聊天回复、代码、幻觉、拒答，甚至类型安全的结构化值。软件要用它，必须先解析 + 校验，且总有跑偏风险 类型安全的结构化值。可能的输出与结构事先定义，模型永不产生类型错误。所有答案附带校准概率与置信度
采样方式 串行：一次一个 token，每个依赖前一个 并行：单次查询生成全部输出。极高效且硬件友好

速度 端到端 3 秒 – 329 秒 端到端 70ms – 500ms，对 System One 形状的查询可达 40×–200× faster
置信度 即使被提示给出置信度估计，模型也倾向过度自信且不一致。如果一个模型 95% 情况下能做对任务，却不说什么时候落在那个 5% 里，这个任务就无法自动化 每个输出都带置信度与不确定性。且是校准的：更高的置信度对应更高的准确率；对相似输入返回相似答案，更一致
典型用例 人在回路任务（聊天机器人、copilot、编码 agent）——强大但需要人工监督；可验证问题（数学证明、内核优化）；快速原型 Demo AI 驱动的工作流 / 智能 if 语句：结构化输出作为模糊决策规则嵌入普通软件（分类、路由、评分、抽取、分支）。周围代码约束其自由度，使其易于组合成可靠系统。大数据 Map-Reduce、实时应用、万物核验（评分、判别、验证、护栏、越狱检测）

核心机制

理解 State 输入、三个决策原语、结构化 Criteria、Confidence 阈值、RLCD 训练方法，以及速度提升的机制。

State：三种输入形状

来自 docs.typesafe.ai/concepts/state：

格式 适用场景 官方示例
String 一条消息、一篇文章、一段文字 "My card was charged twice."
Object 有名字段、相关记录、应用状态 {"message": "My card was charged twice.", "order_id": "A-104"}
Array 一组消息或记录的序列 ["Hi", "My customer number is TS1337.", "My card was charged twice."]

硬性约束：

  • 一次请求评估一个 state，全部问题共享同一个 state，独立并行评估。
  • 上下文：64k token 覆盖 state + 全部问题；32k token 覆盖 state + 单个最长问题。
  • 仅支持文本输入。图片、音频、视频暂不支持。

Noul / Choice / Score：三个决策原语

官方把 Choice / Score / Noul 称为 AI 原语（AI primitives）——「像软件原语一样，模块化、可组合、结构化、可靠、快速」。

原语 回答什么问题 返回什么 配置上限 典型用途
Choice 「这些选项里选哪个？」 choice（选中项）+ probabilities（每个选项的概率，和为 1）+ confidence 最多 255 个选项 工单路由、文档分类、意图识别
Score 「在第几级？」 score（可落在层级之间的小数）+ legend（层号→描述）+ probabilities + confidence 最少 2 级，最多 10 级 严重度、客户情绪、简历匹配度
Noul 「这句话是否为真？」 noul（0–1 之间的概率值，无 confidence，概率本身即答案） — 是否紧急、是否有欺诈迹象、是否有害

「Noul」是 TypeSafe 自造词。含义是「命题为真的概率」——noul: 0.81 表示该命题有 81% 的概率为真，不是「强度 81 分」。很多人第一次用会搞错（腾讯云社区特别提醒）。

Level 描述方式 score confidence

Confidence：公式与阈值分流

docs.typesafe.ai/confidence：

  • confidence 由 probabilities 派生，取值 0–1。
  • Noul 没有 confidence（概率本身就是答案）。
  • 文档内嵌交互式 demo 披露的公式：
choiceConfidence = (count × peak − 1) / (count − 1)

# 三选项时即：
choiceConfidence = (3 × largest − 1) / 2

官方推荐的三段式用法（原文）：

置信度 动作
High 自动执行（Act automatically）
Medium 谨慎推进（Proceed with caution）
Low 不执行（Do not act）

官方风控分层代码示例（逐字保留）：

if confidence < 0.5:
    route_to_human(user_message)          # Model is genuinely unsure. Don't guess.
elif action.choice == "check_balance":
    show_balance(account_id)              # Low stakes. Recoverable.
elif action.choice == "approve_transfer":
    if confidence > 0.9:
        confirm_then_execute(account_id)  # High stakes, high confidence.
    else:
        ask_user_to_confirm(account_id)   # High stakes, moderate confidence.

⚠️ 重要提醒（来自独立验证）：有研究者在 16,000+ 次多选答案上验证，confidence 恰好等于 (最大概率 − 1/K) / (1 − 1/K)——即它就是最大那个概率的线性重标定，不构成对「答对与否」的独立校验。也就是说 confidence 高不代表对，它只是「最大概率有多突出」的另一种写法。不要把 confidence 当独立的第二信号使用。

RLCD：训练方法

docs.typesafe.ai/introduction/machine-learning-primer：

三种后训练路线：

缩写 全称 训练目标 产出
RLHF Reinforcement Learning from Human Feedback 人类评分者偏好的回复 聊天模型
RLVR Reinforcement Learning with Verifiable Rewards 可被程序化验证的输出 推理模型，但更慢更贵
RLCD Reinforcement Learning for Calibrated Decisions 在 System One 任务上、认知诚实的概率 决策模型（Jev）

校准的官方定义（原文）：

Outcomes assigned a probability of 0.2 should occur about 20% of the time. Outcomes assigned a probability of 0.8 should occur about 80% of the time. Outcomes assigned a probability of 1.0 should occur 100% of the time. These rates describe groups of predictions, not a guarantee about any single answer.

官方对 RLHF 的批评：会导致 mode dropping（偏好某风格、降低其他输出概率），是 mode collapse 的轻量版。「An output can be compelling to a person without being reliable enough for unattended automation.」（一个输出可以对人很有说服力，却不够可靠到可以无人值守自动化。）

独立技术解读（复旦 Di Zhang，博客） —— 对 RLCD 最锐利的一份分析：

  • 把 RLCD 解为 schema 条件化的 Plackett–Luce 目标 + 概率校准；论证 PPRM（Bradley–Terry）只是 Luce 的 K=2 特例。
  • 核心金句：「the reward model is no longer hidden behind a generator. The reward model becomes the model.」（奖励模型不再藏在生成器背后，奖励模型本身变成了模型。）
  • 另一句：「Jev is what happens when the reward model stops grading the product and becomes the product.」
  • 指出 TypeSafe 称有「新架构 + 并行采样器」，但未发布新注意力算子、无采样算法、无复杂度结果、无消融实验。

⚠️ 同名陷阱：2023 年另有一篇 RLCD: Reinforcement Learning from Contrastive Distillation（arXiv:2307.12950）——同名但完全不同的东西。搜索 RLCD 时务必区分。

速度提升的机制

机制 官方说法 独立验证结果
非自回归单次前向 传统 LLM 逐 token 生成，「即使只输出 A，也要先输出 'The answer is' 再输出 'A'」。Jev 完全跳过自回归解码，单次并行前向传播直接在隐状态上打分 ⚠️ 多数独立研究者认为这不需要改模型。Sean Goedecke 用 ~150 行 Python 在 Qwen3-8B 上实现，并论证：「this doesn't require changing the model. As long as you have access to the logits and can prefill data into the prompt, you can turn any LLM into a general fast classifier.」
多问题并行评估 LLM 每多一个问题就增加串行生成时间；Jev 在同一前向中评估全部问题，所以延迟与问题数几乎无关，稳定在 70–500ms ✅ 已被官方 Cookbook 实测印证（参见「批量提问与 Parallel Questions」）
RLCD 保证校准 官方称 Jev 说 95% 时，统计上 95% 这类答案确实正确 ⚠️ 这是需要验证的校准问题。官方至今未公布任何 calibration curve 或 ECE 数字；多个独立测试发现反例（参见「概率校准与数据分布」）

用户自建复现的实测对照（Sean Goedecke 博客）：

方案 决策吞吐

    response = client.system_one(
        state={"document": "I was charged twice. Please fix this ASAP."},
        questions={
            "billing": Noul(instructions="Is this ticket about billing?"),

                instructions="What is the customer's tone?",

                criteria=["can wait", "this week", "today"],

print(response.nouls["billing"].noul)        # e.g. 0.97
print(response.choices["tone"].choice)       # e.g. "frustrated"
print(response.scores["urgency"].score)      # e.g. 2.05  ← 可落在层级之间

这段代码里最值得注意的三点： ① 一次调用同时问三类问题——不是三次调用，全部在同一个前向传播里并行评估； ② criteria={"calm": None, ...} 里的 None 是官方约定的「该选项无需额外说明」（use null when an option needs no extra detail）； ③ score 是 2.05 这种小数，不是整数——Score 返回的是概率加权位置，不是被选中的层级编号。

评测方法与口径

  1. 全站未出现任何 ECE（Expected Calibration Error）数字。 官方最核心的卖点是「校准」，但评测站只给准确率/成本/延迟三类数字，没有任何一条 calibration curve 或 ECE 数值。这与「独立测试普遍测出 ECE」形成鲜明对比（参见「概率校准与数据分布」）。
  2. Jev 的准确率并非最高。 平均 67.8%，落后于 sol（74.1%）、opus 5（73.1%），与 terra（67.9%）基本持平。Invoice Processing 上仅 61.8%，明显落后（sol 79.1%）。Jev 赢的是成本（低 2–3 个数量级）与延迟（低 1–2 个数量级）。
  3. 所有数字是「与 consensus 标签的一致性」，不是绝对正确率。 而 consensus 标签来自「GPT-6 Astra + Claude Fable 5.1 输出概率的平均值」——不是人工 ground truth。这意味着：如果两个前沿模型共同犯错，Jev 答对反而会被记为「答错」。

用 Adapter 连接通用模型

官方定位：drop-in 替换 typesafe_sdk 的 system_one 评估 API，用 LLM 后端（OpenAI / Anthropic / Gemini）代替 TypeSafe，用于对比成本/速度/智能。

关键点：无需 TypeSafe API Key 即可开发——用各家 LLM 的 Key 就能跑通同一套 Choice / Score / Noul 接口。

完整选项表（README 原文）：

选项 含义
structured_outputs 用 provider 原生结构化输出，否则提示 JSON 并在客户端校验
llm_answer_mode "probabilities"（每标签一个分布）或 "discrete"（每问一个值）
normalize_probabilities 把不合法概率分布缩放为和为 1

官方 README 原文要点：

  • 定位：「An ultra-fast, local-first "System 1" browser automation engine & Agent Skill for Claude Code, Codex, and Cursor」
  • 模型：本地 Qwen3.5-9B / Qwen3.5-35B-A3B，经 MLX（Apple Silicon）或 PyTorch（CUDA/CPU），零云推理
  • 核心机制：Single-Token Logits Scoring（O(1) Reflexes）——扫描渲染后的 DOM，只取可见可交互元素，格式化为离散候选元组 (CLICK, btn_7)，把候选动作动态映射到词表中的单个 token（A/B/C…），单次前向传播对候选 logits 做 Softmax 打分，从而完全跳过自回归解码
  • 打分公式（README 原文）：P(cᵢ|Context) = exp(zᵢ/T) / Σexp(zⱼ/T)
  • 候选形式示例：("CLICK","btn_search")、("SELECT","opt_timezone_sg")、("TYPE_TEXT","input_query")、("DONE","task_completed")
  • 只有 TYPE_TEXT 时才调用小模型生成字符串
  • 自称「Open-Source Reverse Engineering of Jev」，声明灵感来自 Jev Ultrafast、openjev、Qwen-2.5-1B-RLCD

与 JSON 模式及 Structured Outputs 对比

这是工程师的第一反应：我不就是让 LLM 输出 JSON 吗？

官方回应：valid JSON 只固定了格式——「forcing an LLM into that format can leave some of its intelligence on the table」（把一个 LLM 强塞进那个格式，会让它的一部分智能留在桌上）。TypeSafe 是从头为结构化决策训练一个 System One 模型，所以概率是模型产生的，而不是提示词请求来的。

已知缺陷与工程缓解

参见「九类已知失败模式」 的 9 类失败模式。工程上最需要注意的四条：

缺陷 官方原文 代码层缓解
计数不可靠 「recognizes the shape of an answer rather than tallying」 在代码中循环，每项一个 Noul

概率校准与数据分布

Alex Molas 的核心论证：校准不是模型单独属性，而是「模型 × 数据分布」的属性。

「for the same input and prompt, Jev will provide the same probabilities to both companies, regardless of their different underlying data distributions. Therefore, the model may be calibrated for one company but not for the other.」

这不是悬而未决的猜测，而是已经被四方独立来源证实的问题。以下按来源排列，从官方自己的承认开始。

四方独立来源收敛到同一结论：输出格式不是安全边界。

官方自己的承认（model-jaggedness/jev-1.13）

Check Point Research（2026-09-24）

  • 场景：把 Jev 放进尽调助手，读 PonziCorp 报告出风险判决。
  • 全部 9 种攻击 × 难度组合至少成功一次
  • 最强攻击 27 次跑通 25 次，平均第 4 轮得手，每次成功约 0.50 美元

金句：「They constrain what a model can say, not what it can be convinced of.」 「did its job correctly, on false evidence」 「is it safe to expose Jev to untrusted input with nothing around it? It is not. Neither is anything else we tested.」

arXiv:2609.28613（南洋理工大学 Tiantong Wu、Wei Yang Bryan Lim，2026-09-23）

  • 用 InjecAgent 全部 510 个直接危害案例重建为类型化决策，对固定版本 jev-1.13.0 发起 54,060 次调用。
  • 攻击「shifts action probabilities but rarely causes Jev to select the attacker's target」
  • 自适应攻击使攻击者目标选择的成功率从 1.8% 升到 3.5%
  • 反直觉发现：经典「Ignore all previous instructions」在 Jev 上反而降低攻击效果
  • 结论：「schema-defined outputs change but do not eliminate prompt-injection risk」

VentureBeat + Octomind + Pydantic + LangChain

  • Pydantic 官方 Jev 文档警告：「the order of a Literal's options or an Enum's members is part of what Jev sees, and reordering them can move the answer」「Jev treats the state as data, not as hostile」
  • Octomind 工程师实测：问是否拦截 rm -rf ~/.ssh，block 概率 0.76 / confidence 0.64；加入伪造的「已预授权」工具输出字段后，block 概率掉到 0.48 / confidence 0.22

选型结论

围绕接口价值、任务边界、准确率与成本，判断哪些场景适合接入 Jev，以及哪些场景需要其他方案。

核心判断

Jev 的接口设计具有直接的工程价值。它把提示词中的判断动作，变成类型安全、带概率的函数调用。架构、校准和准确率仍需要结合具体业务数据评估。

选型时的五个判断

  1. 「无幻觉」= 不会输出非法类型 ≠ 判断正确。 官方自己承认 0% 是数学推导不是实测。这是最重要的一条。
  2. 官方 193.6×/444.6× 不是可引用的通用倍数。 四个限定条件缺一不可；可核实的同类封装下倍数是 10×，按官方定价页算便宜是 8.5×。
  3. 速度优势主要来自推理策略，不是新架构。 任何 LLM 只要你能拿到 logits，都能变成 System One 模型（Sean Goedecke 用 150 行 Python 证明）。
  4. 真正的护城河是「校准 + 世界知识」，而这恰恰是还没被独立验证清楚的部分。 官方至今未公布一条 calibration curve。
  5. 接口设计确实有价值，值得学。 即使你不用 Jev，「把判断从提示词里拿出来，变成一个类型安全的函数调用，加置信度阈值分流」这个模式本身是正确方向——你完全可以用本地小模型 + 少量标注自己实现，甚至可能更准更快更便宜。
